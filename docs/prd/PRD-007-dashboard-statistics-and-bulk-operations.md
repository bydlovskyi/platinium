# PRD-007 — Dashboard Statistics, Bulk Operations & Role-Based Permissions

## Problem Statement

The portal manages three entities competently but tells an administrator nothing. The
route they land on after signing in is a placeholder. Someone opening the portal on a
Monday morning has no way to answer "what is the state of things?" without opening
three lists and reading them.

Three further gaps are visible once the CRUD screens exist:

**Repetitive work has no leverage.** Archiving forty tickets after an event ends means
forty edit-save cycles. PRD-003 already delivers row selection, but nothing consumes it,
so the checkboxes are currently decorative.

**Data cannot leave the portal.** Administrators reconcile against spreadsheets, and a
filtered list that cannot be exported forces manual retyping.

**Every session has unlimited power.** There is one role and it can delete anything. A
platform with multiple concurrent administrators — which `TECHNICAL_REVIEW.md` must
address — needs at least the structural distinction between someone who can change data
and someone who can only read it. PRD-002 put the role field on the user record
precisely so this could be built without touching the contract again.

These are the assessment's bonus features. They are grouped into one PRD because they
share a property: each one depends on all the CRUD work being finished, and each one is
a thin layer over machinery that already exists. Scattered across four PRDs they would
look like four afterthoughts; together they form the layer that turns a set of CRUD
screens into an operations tool.

## Solution

**A dashboard that answers the Monday-morning question.** Headline figures — total
events, how many are currently running, total tickets, total inventory, and gross
inventory value broken down per currency. A breakdown of tickets by status and of
events by status. A list of the next events starting, and a list of tickets whose stock
is nearly exhausted, each linking into the relevant filtered list.

Every figure is computed by a single aggregate endpoint on the mock, not by fetching
lists and reducing them in the browser. That is the only version of this feature that
would survive a real dataset, and building it the other way would contradict everything
`TECHNICAL_REVIEW.md` says about scale.

Value is **never summed across currencies**. A single total mixing euros and pounds is
not a number; it is a bug with a friendly face. The dashboard shows one figure per
currency.

**Bulk operations over the existing selection.** With rows selected, a contextual bar
offers the operations that make sense for that entity: status change and delete for all
three, with delete subject to the same dependency rules as a single delete. Results are
reported per record — the operation reports how many succeeded and how many were
blocked, and why. A bulk operation that reports only "done" when a third of it failed is
worse than no bulk operation.

**CSV export of what is on screen.** Export respects the active filters and sort, not
just the current page, so exporting a filtered view produces the filtered data. The
export is generated by the mock from the same query the list used, so the file and the
screen can never disagree.

**Permissions as a declarative capability check.** Two roles: an administrator who can
do everything, and a viewer who can read. A single capability composable answers "may
the current user do this?", and navigation entries, page actions, row actions and bulk
operations consult it. The router guard enforces it on route metadata, and the mock
enforces it on every write — a UI-only permission is a suggestion, not a permission.

## Implementation Decisions

### Dashboard

A single aggregate endpoint returns the whole dashboard payload in one request. The
alternative — six requests reduced in the browser — would not survive a realistic
dataset, produces six independent loading states, and would make the portal's
scalability claims dishonest.

The dashboard view holds presentation only: statistic cards, breakdown displays, two
short lists. All computation lives in the mock handler, which is where a real backend
would do it.

Currency aggregation returns an array of per-currency totals. No cross-currency total is
computed anywhere, and the absence is deliberate rather than an omission.

The "nearly sold out" threshold is a named constant with a documented rationale, not a
literal buried in a handler.

**Charts are optional.** The figures and breakdowns are the requirement; if a charting
library is added it must be justified by clarity rather than decoration, and it must
respect the dark theme from PRD-002. A breakdown rendered as labelled proportional bars
using existing tokens is acceptable and avoids a dependency.

### Bulk operations

The contract gains one bulk endpoint per entity, accepting a list of identifiers and an
operation, and returning a per-identifier result. A client loop issuing N individual
requests would be N round trips, would have no transactional meaning, and would make
partial failure impossible to report coherently.

Partial success is the expected case, not an edge case. The response carries succeeded
identifiers and failed identifiers with a reason each, and the UI reports both. Bulk
delete respects the dependency rules from PRD-004 and PRD-005: a referenced event or
category is reported as blocked, with its blocking count.

Selection is page-scoped and cleared whenever the query changes. Acting on rows that
have scrolled out of the current filter is the most dangerous bug this feature could
have, and clearing on query change is what prevents it.

A shared bulk-actions composable owns selection state, the confirmation, the request,
the per-record result and the refresh. Entity screens declare which operations they
support.

### CSV export

Export is a query parameter on the existing list endpoints rather than a separate
endpoint, so filter and sort semantics are shared with the list by construction and
cannot drift. The mock returns the full filtered result as CSV with the correct content
type and a filename in the content-disposition header.

Formatting rules: money as a decimal with its currency in a separate column so a
spreadsheet can sum it; dates in ISO-8601 for unambiguous parsing; references by name.
Fields are escaped correctly — a venue containing a comma or a quote is a defect that
only appears in real data.

Above a documented row threshold, the administrator is warned before the export starts.

### Permissions

Two roles: administrator and viewer. The user record already carries the role from
PRD-002; this PRD adds the second seeded account and the enforcement.

A capability composable is the single answer to "may the current user do this?",
expressed as entity-and-operation pairs. It is consumed by navigation entries, page
actions, row actions and bulk operations. Nothing performs its own role comparison.

Enforcement is layered: the UI hides what the user cannot do; the router guard rejects
direct navigation to a route whose metadata requires a capability the user lacks; the
mock rejects the write regardless. Only the third is a real control — the first two are
usability.

### Testing boundary

- Dashboard aggregation in the mock — unit tested against a known fixture set, including
  per-currency separation and the nearly-sold-out threshold.
- CSV serialiser — unit tested: escaping of commas, quotes and newlines; money and date
  formatting; an empty result set.
- Bulk operations composable — unit tested: selection lifecycle, clearing on query
  change, total success, total failure and partial success reporting.
- Capability composable — unit tested for every role-and-operation combination.
- Dashboard — integration tested: renders every figure from MSW, and each link navigates
  to the correctly filtered list.
- Bulk flow — integration tested: select rows, change status, assert the list updates;
  attempt a bulk delete including a referenced record and assert the partial-failure
  report.
- Export — integration tested: triggers with the active filters and receives a correctly
  filtered file.
- Permissions — integration tested: sign in as a viewer and assert that write actions are
  absent, that a direct edit URL is refused, and that a forced write request is rejected.

## API Contract Plan

This PRD owns the following consolidated contract change.

**Endpoints introduced:**

- `GET /dashboard/stats` — the complete aggregate payload
- `POST /events/bulk` — accepts identifiers and an operation; returns per-identifier
  results
- `POST /categories/bulk` — as above
- `POST /tickets/bulk` — as above

**Existing endpoints extended:**

- `GET /events`, `GET /categories`, `GET /tickets` — gain a `format` query parameter
  whose CSV value returns the full filtered result as `text/csv`

**Schema components introduced:**

- `DashboardStats` — counts, per-currency value totals, status breakdowns, upcoming
  events, low-stock tickets
- `CurrencyTotal` — currency and total in minor units
- `StatusBreakdown` — status and count
- `BulkRequest` — identifier list and operation
- `BulkResult` — succeeded identifiers, plus failed identifiers each with a reason

**Existing components extended:**

- `UserRole` — gains the viewer role
- Route metadata gains an optional required capability (client-side; not a contract
  change)

**Authorisation:** every write endpoint rejects a viewer's token with `403`. The
response interceptor from PRD-001 gains a `403` branch that notifies without signing the
user out — a permission failure is not a session failure.

## Out of Scope

- Optimistic UI updates. Considered and deferred: with a mock API responding in tens of
  milliseconds, optimism is invisible to the administrator while adding rollback
  complexity to every mutation. The pattern and where it would pay off are documented in
  `TECHNICAL_REVIEW.md` instead of being built for the demo.
- Drag-and-drop ordering. No entity in this domain has a meaningful manual order.
- Infinite scrolling. Offset pagination is the chosen model; the migration path to
  cursor pagination is discussed in `TECHNICAL_REVIEW.md`.
- CSV import. Import requires column mapping, validation reporting, partial-failure
  recovery and a preview step — a PRD of its own, not a bonus slice.
- Configurable roles, granular per-entity permissions and an administration screen for
  managing users.
- Scheduled or emailed reports, saved dashboard configurations and date-range selection
  on the dashboard.
- Real-time updates. Concurrent-administrator conflict handling is a
  `TECHNICAL_REVIEW.md` topic.
- Excel and PDF export formats.

## Further Notes

Optimistic updates were selected in scoping and are deliberately reclassified here as
documented rather than built. Against a sub-50-millisecond mock the user-visible benefit
is nil, while the cost — rollback handling on every mutation, and reconciliation logic
that cannot be honestly tested without artificial latency — is real. Explaining that
trade-off in `TECHNICAL_REVIEW.md` demonstrates better judgement than shipping a feature
whose value cannot be observed. If it is built anyway, it should be confined to bulk
status changes, where the operation is slow enough to notice, and it must reuse the
PRD-001 chaos controls to prove the rollback path.

The per-currency decision is small and load-bearing. A reviewer scanning the dashboard
for a single "total revenue" figure and not finding one will either notice the care or
ask about it — and the answer is the same either way. Summing across currencies is the
kind of error that ships, because it looks right.

Permission enforcement at the mock layer is what makes the role model more than a
cosmetic exercise. Hiding a button is not access control, and a reviewer testing a
direct write request will find out which one was built.
