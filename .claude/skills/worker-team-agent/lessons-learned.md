## [2026-09-22] Response interceptor & notification service (issue #16)

**Category:** architecture | process
**Context:** Built the global response interceptor and notification service (PRD-001). The acceptance criteria said 401 should "reset the session and redirect to login," but the auth store and login route are a separate, later slice (#19) that hadn't started.

**Lesson:** The cascade-stack sometimes assigns a slice an acceptance criterion that literally cannot be implemented yet because a downstream slice owns the piece it needs (here: a route name and a session store that don't exist). Guessing at the missing piece (e.g. hand-adding a `routeNames.login` the generator hasn't produced yet) breaks type-check or duplicates work the owning slice will redo. The project's own EventEmitter pattern (`helpers.eventEmitter` / `IEventMap` in `src/utils/helpers.ts`) is the intended decoupling point for exactly this: the early slice publishes a typed event describing what happened, the later slice subscribes and does the part it owns.

**Action:** When a slice's acceptance criterion depends on a UI surface or store that a later, not-yet-started slice owns, implement the emit-only half via the EventEmitter and document the forward dependency with a one-line comment plus a PR-body note — don't stub the missing route/store yourself and don't skip the criterion.

**Lesson 2:** Building a notification service surfaced that the design-token foundation slice (#12) only defined `accent`/`danger`/`status-*` tokens, not `success`/`warning`/`info` — and Element Plus's own `el-notification.css` wasn't imported anywhere in the app yet, so `ElNotification`'s `type` prop would have rendered with library-default colors regardless of what tokens existed.

**Action:** Any slice that's the first to actually use an Element Plus component with semantic type variants (notification, alert, tag, etc.) should check both (a) whether the needed semantic tokens exist in `src/assets/styles/tokens.ts` yet, and (b) whether that component's theme-chalk CSS is imported in `src/assets/styles/element-reset/components/index.css` — the design-foundation slice only pre-built tokens for components already in use at the time, not every Element Plus component the app will eventually touch.

## [2026-09-22] Docker multi-stage build (issue #17)

**Category:** architecture | process
**Context:** Building the Docker slice's "produces a working portal with seeded data" acceptance criterion required checking whether the mock backend actually answers requests inside the container's built bundle.

**Lesson:** The browser MSW worker only registers when `import.meta.env.DEV` is true — an explicit, deliberately reviewed acceptance criterion from #15 ("registered in development only, never in a production build"). That's sound advice for a project with a real backend, but this project never has one: `vite build` is what both a hypothetical real deployment and this project's only deployment (the Docker demo) run, so the `DEV` gate silently strips the entire "backend" out of the one build artifact that's supposed to demonstrate the app. PRD-001's Docker section assumes the opposite ("the mock API runs inside the browser... the production image needs no second service"). Neither #15 nor #17's issue body flagged this tension — it only surfaces when you actually trace what `vite build` produces versus what `npm run dev` produces.

**Action:** Did not fix it from the Docker slice — silently loosening another slice's explicit, reviewed acceptance criterion from outside that slice's file scope is a guess, not a verification. Left it as an open question on #17 for a human call: either relax the `DEV` gate to something like "not test mode" so the mock also ships in the Docker/demo build, or scope PRD-001's "seeded data" claim down to dev-only. Any later slice that touches `src/main.ts`, `src/mocks/browser.ts`, or writes TECHNICAL_REVIEW.md's "accepted debt" section should resolve this explicitly rather than re-discovering it.

## [2026-09-22] Session and login — auth store, route guard, login screen (issue #19)

**Category:** frontend | debugging
**Context:** The PRD explicitly flagged "session bootstrap must complete before the first guard evaluation, not merely before mount" as the likely source of a subtle defect in this slice.

**Lesson:** It was real, and gating the bootstrap chain on `router.isReady()` — the obvious-looking fix — does not fix it. `app.use(router)` itself triggers Vue Router's initial navigation (and therefore the first `beforeEach` guard evaluation) the moment it's called, not when `router.isReady()` is later awaited; `isReady()` only resolves whatever navigation decision the guard already made. A bootstrap chain of `enableMockingIfNeeded().then(restore).then(() => router.isReady())` with `app.use(router)` called synchronously up front still lets the guard run against the pre-restore store state, because installing the router happens before any of that chain resolves. Static code reading and a passing type-check did not catch this — it only surfaced under a live Playwright reload test on a protected route. The fix was to defer `app.use(router)` itself into the `.then()` chain, after `restore()` resolves and before `router.isReady()`.

**Action:** For any app-bootstrap ordering problem involving Vue Router guards and async state restoration, verify the fix live (reload a route that should be affected) rather than trusting that "moved code earlier in the `.then()` chain" is sufficient — confirm what actually triggers the guard's first run (installing the router), not just what the chain appears to sequence.

**Lesson 2 (process risk):** A downstream teammate (writing tests) hit what looked like a stray file conflict mid-task and ran `git stash` / `git stash drop` to clear it — not realizing the working tree held substantial uncommitted work from the build phase. This silently reverted several tracked files, including a type augmentation (`dts/global.d.ts`'s `RouteMeta.requiresAuth`/`requiresAnonymous`). The teammate reconstructed most files from what it had read earlier in its own context and reported "type-check passes," which was true but misleading: `RouteMeta` in this project's vue-router version extends `Record<string, unknown>`, so a route guard reading `to.meta.requiresAuth` type-checks fine even with no such property declared anywhere — the augmentation's loss was functionally silent to every automated gate (lint, type-check, and even the tests, which stub `to.meta` directly rather than going through the real augmented type). It was only caught by an independent manual diff of `git status`/`dts/global.d.ts` against what the build phase had actually reported adding.

**Action:** Never run `git stash` (or any history-rewriting git command) mid-task when other work in the same tree might be uncommitted — check `git status`/`git diff` first and resolve the actual conflict directly instead. When a build phase reports "added a type augmentation" and later phases touch the same area, re-diff that specific file against the build phase's own report before trusting a later "type-check passes" — a permissive ambient type (an index-signature-extended interface, `any`, a too-wide union) can make a real regression invisible to the automated gates that are supposed to catch it.

## [2026-09-23] List resource composable (issue #22)

**Category:** process | frontend
**Context:** After a review pass renamed a hand-edited import (`IPaginationMeta` from `src/mocks/db/`) to the canonical ambient global type (`TPaginationMeta` from `src/features/platform/api/dts/index.d.ts`), `npm run type-check` failed with `Cannot find name 'useListResource'` inside the new composable's own spec file — even though the composable itself, its export, and the auto-import entries the build phase had generated all looked correct on inspection.

**Lesson:** `.config/auto-imports/auto-import.json` and `dts/auto-imports/auto-import-scripts.d.ts` are not a static one-time scan of `src/` — unplugin-auto-import (re)populates them as a side effect of an actual Vite-driven run (`npm run dev`, `npm run test`/`vitest`), and a later command in the same session (in this case a second `npm run lint` pass) can leave them showing as unmodified/reverted relative to `main` if nothing Vite-driven has re-touched the new file since. `vue-tsc --build` reads whatever is currently on disk, so if the registry doesn't yet mention a brand-new auto-imported composable, type-check fails on call sites that use it with a name-resolution error — one that looks like a real missing-import bug but isn't.

**Action:** After adding a new auto-imported composable (or renaming/moving one), run `npx vitest run <its .spec.ts>` (or `npm run dev` briefly) *before* trusting a `npm run type-check` failure that says `Cannot find name` on something that's clearly exported and used correctly — that failure often means the auto-import registry is stale, not that the code is wrong. Re-run type-check after the Vite-driven pass regenerates the registry.

## [2026-09-23] Data table component (issue #23)

**Category:** review | architecture | frontend
**Context:** Built the descriptor-driven `AppDataTable` (PRD-003). The issue's own acceptance criterion "sort cycles through ascending, descending and unsorted on repeated header activation" turned out to depend on `useListQuery.setSort` from the already-merged issue #21/#22 branch, which only toggled ascending/descending and never returned to unsorted — a real 2-slice-old bug that #23's component-level spec masked by faking the three states via `wrapper.setProps(...)` instead of driving them through the real composable.

**Lesson:** When a slice's own acceptance criterion is phrased as end-to-end behavior ("clicking X cycles through states") but the component being built only emits an intent event, the criterion isn't actually verified until something drives that intent through the real upstream piece that owns the state machine — even if that piece was merged in a prior slice. A test that fakes the far end of that chain via `setProps`/mocked props can pass green while the real wiring is broken. This was caught by an independent multi-agent review pass (architecture-reviewer and e2e-reviewer both flagged it from different angles) rather than by the build agent's own verification, which only checked its own new files.

**Action:** For any slice whose acceptance criteria describe interaction outcomes ("cycles through", "resets to", "restores") rather than pure rendering, trace whether the actual state transition lives in this slice's files or an upstream composable/store from an earlier slice, and add/extend a test at *that* layer (not just a props-faked component test) before declaring the criterion met. It's legitimate to fix a small, contained bug in an already-merged file when it's the literal blocker for the current slice's own acceptance criterion — that's different from scope creep into another *open* slice's file ownership.

**Lesson 2:** Element Plus's `el-checkbox` does not forward arbitrary passthrough attrs (e.g. `aria-describedby`) to its inner `<input>` — only to the outer wrapping `<label>`/`<span>` root, per its SFC source (`checkbox2.mjs`, which hardcodes the input's bindings with no `v-bind="$attrs"`). An `:aria-describedby` bound directly on `<el-checkbox>` silently lands somewhere a screen reader won't associate with the focused control. Verified by mounting and asserting on the actual rendered `<input>` rather than trusting that a bound prop "worked" because Vue didn't error.

**Action:** For any accessibility attribute applied to an Element Plus form component wrapper (checkbox, radio, switch), verify in a mounted test which DOM node it actually lands on before relying on it — prefer folding the needed context into a prop the component explicitly declares and binds to the real control (here, `aria-label`) over assuming attrs fallthrough reaches the native input.

**Lesson 3 (process):** Multiple independent review/debug agents (state-machine hypothesis, accessibility hypothesis, e2e-reviewer, architecture-reviewer) converged on the same two real bugs from different angles in parallel — the redundant coverage was worth the cost here; a single reviewer would likely have caught only one angle. Also: `git diff main...HEAD` returns empty for work still fully uncommitted on a branch tip that already points at a merge commit — reviewers need to fall back to `git status`/`git diff` against the working tree, not just the branch-vs-main diff, or they silently review nothing.

## [2026-09-23] Events list — first PRD-003 consumer (issue #26)

**Category:** frontend | review | process
**Context:** Built the events list screen, the first real consumer of `useListQuery`'s `resetFilters` and `AppDataTable`'s `clear-filters-requested`/`ListToolbar`'s `clear-all-requested` emits (both existed since #22/#24 but had never been wired to a live screen before).

**Lesson:** `useListQuery.resetFilters()` only ever reset the `filters` object, never `search` — invisible in every prior unit/integration test because those tests exercised filters and search independently, never the combination "search is the only active query param, it matches nothing, click the empty state's 'Clear filters' button." Static review (architecture/security reviewer reading the diff) did not catch it either, because the composable's own code looked internally consistent — the gap only showed up by actually driving the rendered empty state in a browser and clicking the real button, which is exactly the scenario `AppDataTable`'s own copy ("Try clearing them to see the full list") promises. Type-check, lint and the full test suite were all green while this was broken.

**Action:** When a slice is the *first* real UI consumer of a shared composable/component's action-emitting affordance (a "clear", "reset", "retry" button wired straight to an existing method), don't assume the existing method's test coverage proves its behavior is complete for the new context — drive the actual rendered control in a live browser check and verify the promised outcome, not just that the method runs without throwing. This is the same shape as the #23 lesson (three-state sort cycling depended on an upstream composable's bug) but for a "clear/reset" affordance instead of a state machine — the general pattern is: any acceptance criterion phrased as a promise about end state ("shows the full list again", "resets to unsorted") needs to be verified by actually reaching that end state through the real control, not by reading the code and reasoning it should work.

## [2026-09-23] Events form — create/edit, unsaved-changes guard (issue #27)

**Category:** debugging | frontend | process
**Context:** Built the events create/edit form (`EventForm.vue`, shared by both routes) plus a new generic `useUnsavedChangesGuard` composable. Lint, type-check and the full test suite (including the form's own unit/integration specs) were all green after the first build pass.

**Lesson:** Two real races survived a clean build and a full green test suite, and both only surfaced under an adversarial debug pass that actually drove the running app rather than reading the diff: (1) the submit handler set its in-flight guard flag *after* `await formRef.value.validate()` resolved — Element Plus's `validate()` is `async` and yields a microtask even when every rule is synchronous, so N rapid clicks/Enter-presses issued before the first `validate()` resolved all read the flag as `false` and all fired a request (confirmed live: 3 rapid clicks → 3 `POST` requests → 3 duplicate rows). (2) `EventForm.vue` is reused by Vue Router across `/events/:idA/edit` → `/events/:idB/edit` navigations with no per-request id check, so a late-arriving response for the *previous* id silently overwrote the form (and the dirty-tracking baseline used by the unsaved-changes guard) with the wrong record's data if the admin navigated to a second edit URL before the first one's request resolved — worse, it also cleared the dirty flag, so the guard would not even warn before a `PATCH` wrote the wrong data into the wrong record. Neither race has a natural unit-test shape (both need genuinely concurrent/reordered async resolution, not just "await it and assert"), which is exactly why a green suite didn't catch them — they were only caught by literally clicking a button three times fast and by delaying one network response via Playwright route interception to force a reversed resolution order.

**Action:** For any form component that (a) is shared across multiple route instances of the same component (create/edit, or edit of different ids) and issues its own network request per mount/param-change, or (b) sets an in-flight/submitting guard flag around an `await`, don't trust "the tests pass" as proof the guard is race-free — explicitly ask two questions before calling it done: "what happens if this fires twice before the first `await` resolves?" and "what happens if a second instance's params change while a request from the first is still in flight?" Verify the answer live (rapid double-click; delayed-response navigation-away-and-back) rather than reasoning from the code, the same pattern as the #23/#26 lessons above but for concurrency races specifically rather than missed wiring. The fix shape for both is cheap once found: set the guard flag synchronously before the first `await`, in a `try/finally`; and re-check the request's own identifying param against current state right before applying its response, discarding it silently if they no longer match.

## [2026-09-23] Categories — first zero-filter list, first real modal (issue #30)

**Category:** review | architecture | frontend | process
**Context:** Built category CRUD (PRD-005) — the first entity with no list filters at all, and the first real consumer of the modals infrastructure (previously only a placeholder `HomeModal`). Automated build + static review (architecture/security) both came back clean; two real bugs and one design gap only surfaced during the mandatory live browser pass.

**Lesson 1 (shared-component defect, only visible at zero):** `ListToolbar`'s mobile view unconditionally rendered a "Filters" button + `el-drawer`, regardless of whether the entity screen supplied anything into the `#filters` slot. Every prior consumer (events) had real filters, so this was invisible until the first entity with *zero* filters exercised the mobile path — the button then opened a genuinely empty drawer. Neither the architecture/security review pass nor the automated test suite caught it (existing `ListToolbar.spec.ts` cases for the mobile badge/drawer didn't bother supplying a `#filters` slot either, since every real caller always had one). Only surfaced by actually resizing to 375px and clicking the button in a live browser. Same shape as the #26 `resetFilters` lesson: a shared component's "looks internally consistent" behavior can hide a missing guard for the *absence* of the thing it renders around, and that guard only gets exercised by the first caller who doesn't have it.
**Action:** When a slice is the first consumer of a shared list/toolbar/table component that supplies *less* than every prior consumer (fewer filters, no columns, no actions), explicitly test the "supplies none" path live, not just the "supplies some" path — a `v-if` that checks a prop's *content* (has the slot got anything in it) rather than just its *existence* is easy to skip on a component that's only ever been fed real content before.

**Lesson 2 (shared-column-based sort UI, non-column sort field):** `AppDataTable` only supports sorting via a visible column's header (it calls the underlying `el-table`'s `.sort(field, order)`, which needs a matching `property` on some rendered column). PRD-005 asked for "sort by name and creation date" but only two columns (name, description) — no `createdAt` column exists to sort through. The straightforward workaround (a small separate "Sort by" `el-select` pushing query params directly) is fine and was already anticipated as necessary, but the first pass wired it by simply passing the active sort straight through to `AppDataTable`'s `:sort` prop unconditionally — since `el-table`'s internal store looks up the column by `property`, sorting by `createdAt` (no matching column) made that lookup silently fail, leaving whatever *column* was last sorted (e.g. `name`) visually stuck showing an arrow that no longer matched what was actually applied. This was caught by an independent adversarial debug pass reasoning "does the header indicator disagree with the actual request" from first principles, then confirmed live; a static review reading the diff did not catch it.
**Action:** Whenever a list adds a sort mechanism that bypasses a shared data-table's own column-header sorting (because the sort field has no visible column), don't pass the "real" active sort state straight through to the table's own `:sort`-type prop unconditionally — gate it so the table only receives a value when the active field actually corresponds to one of its rendered columns, otherwise pass `undefined`/unsorted. Verify live by switching between the two sort mechanisms and checking the header indicator agrees with the request each time, not just that both eventually produce the right data.

**Lesson 3 (interceptor default masks a caller's real signal):** The response interceptor's 409 handling forced every conflict body into `DependencyConflictError`'s `{entity, count}` shape, defaulting missing fields to `''`/`0`. That was silently wrong for the categories contract's duplicate-name conflict (a coded, entity-less `{code: 'DUPLICATE_NAME', message}` body) — the caller had no reliable signal to distinguish "this is a uniqueness clash" from "this is a real dependency conflict with a defaulted/missing count," short of inspecting a field that a real dependency conflict would never actually leave at its default. Fixed by branching on whether `entity`/`count` are actually present in the body before deciding which error class to construct, and adding a second, `code`-carrying error class for the coded case. A pre-existing test had encoded the old (wrong) fallback as the expected behavior, so fixing the interceptor required updating that test's assertion, not just adding a new one.
**Action:** When a shared error-mapping layer (interceptor, error boundary, etc.) defaults missing fields to build a caller-facing object, check whether "the fields are actually absent because this is a different case entirely" is possible before trusting the default — a `?? ''`/`?? 0` fallback that never fires for the case it was written for, but fires routinely for a second, structurally different case, is a sign the two cases need distinct types, not a shared one with defaults papering over the difference.

## [2026-09-23] Tickets contract — first cross-entity referential validation (issue #31)

**Category:** backend | debugging | review
**Context:** Built the tickets API contract (PRD-006): a mock handler validating `eventId`/`categoryId` foreign-key references against `db.events`/`db.categories` before accepting a create or update. Automated build (lint/type-check/39 tests) was clean on the first pass; an adversarial post-build bug hunt (not the static architecture/security review, which missed it) found a real data-corruption bug via direct HTTP reproduction rather than code reading alone.

**Lesson:** A per-field "only validate when the field is present on the payload" convention (used throughout this codebase's `validate` functions, e.g. `events.ts`'s `countryFormatError`/`statusFormatError`, so a `PATCH` omitting a field isn't re-validated against nothing) has to agree with whatever the storage layer actually treats as "absent." Here, `eventReferenceError`/`categoryReferenceError` special-cased `''` (empty string) as "absent, leave it alone" — reasonable-looking, since `requiredFieldErrors` already treats `''` as missing on *create*. But `src/mocks/db/collection.ts`'s `definedFieldsOf` (which builds the actual patch object applied on `PATCH`) only strips keys whose value is `undefined`, not `''`. So `PATCH { eventId: '' }` skipped the referential check (treated as absent) *and then* got persisted verbatim by `collection.update`, silently corrupting the record (an orphaned ticket, `eventName` degrading to a fallback string on every future read) with a `200` response and no error surfaced. Neither the architecture-reviewer nor the security-reviewer agent caught this from reading the code — both concluded the validation was sound. It only surfaced when a separate bug-hunt pass sent an actual `PATCH` with `eventId: ''` and inspected the stored record afterward.

**Action:** Whenever a `validate` function's "present vs. absent" check uses anything other than a strict `!== undefined` test (e.g. also excluding `''` or `null` as a convenience, especially by copying a `create`-path convention onto an `update`-path function), trace it against the literal function that builds the persisted patch (here, `definedFieldsOf`) to confirm they agree on what "absent" means — a static review that only reads the validator in isolation, without cross-referencing the persistence layer's own definition of "unset," will not catch the mismatch. For any new referential-integrity check (foreign key style validation), test the empty-string case explicitly and assert on the *stored* record afterward, not just the response status — a `200`/`400` alone doesn't reveal whether a rejected-looking value was actually written.

## [2026-09-23] Currency input — a watcher that reads its own already-updated model (issue #32)

**Category:** frontend | review | process
**Context:** Built `CurrencyInput`, the sole minor-unit↔decimal conversion boundary (PRD-006). A `watch(() => props.currency, (newCurrency, oldCurrency) => {...})` was meant to preserve the displayed decimal amount across a currency switch by reading `minorUnits.value` (the `defineModel` ref) inside the handler and treating it as "the amount at the old precision." Automated build (lint/type-check/tests, including two dedicated currency-change tests) was clean on the first pass; an adversarial debug pass — not the static architecture/security review, which found nothing wrong — caught both a real bug and a test gap.

**Lesson:** Vue applies a simultaneous prop/model update *before* running the watcher that observes a different but related source, so a `watch(singleSource, handler)` that reads a second, independently-mutable piece of state from inside its handler is implicitly assuming that second piece hasn't also changed in the same tick. Here, if a parent ever sets `currency` and the `modelValue` together (e.g. a ticket-edit form loading a fetched record's price and currency at once), the handler read the *already-new* `minorUnits.value` and wrongly reconverted it as if it were still expressed at the old currency's precision — silently corrupting the amount. It was undetectable by static review and invisible in the test suite for a structural reason, not an oversight: this project's only three currencies (`USD`/`EUR`/`GBP`) all share two decimal places, so "reconvert" and "leave alone" produce the identical number, and the two existing currency-change tests passed under a deliberately-broken no-op watcher (confirmed by patching it out and rerunning). A closed, same-precision enum is exactly the condition under which this class of bug hides.

**Action:** When a watcher's job is "preserve derived state across a change in *one* of several related reactive sources," watch all the related sources together (`watch([sourceA, sourceB], ([newA, newB], [oldA, oldB]) => ...)`) rather than one alone — the combined old/new pairs are what let the handler distinguish "A changed by itself" from "A and B changed together," which a single-source watcher reading the other source's *current* value cannot do reliably. Separately: when a test's only currency/enum values happen to share a property (here, precision) that the code under test is specifically supposed to handle *differences* in, that similarity can make an incorrect implementation pass — prove the test would fail against a naive/no-op version (temporarily revert the fix and rerun) before trusting it as regression coverage, and where the real domain values don't yet exercise the difference, stub the derived property (`vi.spyOn`) rather than relying on the production enum to eventually grow a differing case.

## [2026-09-23] Remote select — el-select's own debounce, and an unobservable-in-jsdom scroll trigger (issue #33)

**Category:** frontend | process
**Context:** Built `RemoteSelect`, the generic remote/paginated `el-select` wrapper (PRD-006's second deep module). Component tests mount the real `el-select`, no stubs.

**Lesson 1 (redundant debounce, only visible by actually testing the debounce):** `el-select`'s own `debounce` prop (default `300`) already debounces before it ever calls `:remote-method` — the first implementation pass didn't know this and wrapped `onRemoteMethod` in its own `useDebounceFn(runSearch, 300)`, producing two stacked 300ms delays (one inside `el-select`, one in this component) on every keystroke. Nothing caught this until writing the debounce test itself: driving fake-timer keystrokes and asserting the resulting `fetchOptions` call revealed `el-select` only calls `:remote-method` once *after its own* debounce settles, so the component's second debounce added a second, redundant wait on top — worse, in one fake-timer sequence the two competing timers actually raced against this component's own scroll-triggered `loadMore` and produced a wrong page-2 call instead of the expected page-1 search call. Removing the component's own debounce (call `runSearch` directly from `:remote-method`, let `:debounce="300"` be explicit on `el-select`) fixed both the redundant-delay UX issue and the race.
**Action:** Before wrapping any Element Plus prop callback in a hand-rolled debounce/throttle, check whether the component already exposes that as a native prop (`el-select`'s `debounce`, but likely others too) — grep the installed `element-plus/es/components/<name>/src/*.mjs` for the prop name before assuming you own that concern. A component test that actually exercises the timing (not just "was the callback eventually invoked") is what surfaces stacked/duplicate debouncing; a purely-static review of the code reads as correct either way.

**Lesson 2 (jsdom has no real layout, so infinite-scroll fires on open, not on scroll):** jsdom returns `0` for `scrollHeight`/`clientHeight` on every element, so VueUse's `useInfiniteScroll` treats every scrollable container as already "at the boundary" the moment it's observed — it doesn't need an actual `scroll` DOM event to trigger `onLoadMore` in this environment. Separately, jsdom also doesn't implement `IntersectionObserver` at all, and `useInfiniteScroll` depends on `useElementVisibility`, which silently no-ops (feature-detected, not thrown) without it — so without a polyfill the scroll trigger is *permanently* inert instead of just untestable-via-literal-scroll. Added `tests/support/intersection-observer.ts` (a synchronous fake reporting every observed element as fully intersecting), following the same pattern as the existing `match-media.ts` polyfill for a different missing jsdom API.
**Action:** Any future component using VueUse's `useInfiniteScroll`/`useElementVisibility`/anything IntersectionObserver-based needs the `tests/support/intersection-observer.ts` polyfill imported (already wired globally into `tests/setup.ts`, so this is automatic for new specs) — don't rediscover the "isElementVisible stuck at false forever" symptom from scratch. When testing such a component, don't try to assert the trigger fires *specifically because of* a dispatched `scroll` event in jsdom — assert on the actual outcome (the next page's data appearing) and document in the test that jsdom's zero-layout is what makes literal-scroll-gesture simulation impossible here, the same way this component's own test does.

## [2026-09-23] Ticket form — two RemoteSelects and a conditional CurrencyInput in one form (issue #35)

**Category:** process | debugging
**Context:** Built `TicketForm.vue`, the first component to compose two `RemoteSelect` instances plus a conditionally-mounted `CurrencyInput` together. Automated build (lint/type-check/567 tests) and both static review passes (security, architecture) were clean. A live Playwright e2e-review pass reported a critical, cleanly-isolated-looking bug: clicking the primary submit button did nothing (no network request, no navigation), while pressing Enter in a text field correctly submitted — reproduced "3 times across fresh page loads" by that reviewer, with `elementFromPoint`/synthetic-event probing pointing at the native-submit path specifically.

## [2026-09-24] Motion and micro-interactions (issue #42)

**Action:** Before writing a component test that asserts on `getComputedStyle` reacting to a `prefers-reduced-motion`/any `@media`-gated CSS custom property, verify empirically (a 5-line throwaway spec, not a doc lookup) whether jsdom's `getComputedStyle` actually resolves `@media` blocks at all — it does not, for any query, regardless of `matchMedia`'s return value. When it can't, split the assertion into what jsdom-testing environment actually can verify (a JS-driven behavioural bypass; a static read of the CSS source proving the override exists and targets the right variables) and use a live browser pass (`browser_emulate_media`) to close the gap on the part that's structurally untestable in the unit/integration suite — say so explicitly in the test's own file comment so a future maintainer doesn't "fix" the test into a false sense of cascade coverage.

**Lesson 2 (`@vue/test-utils` stubs `<TransitionGroup>` by default, so a component test asserting a leave-transition class on the *stub* is a false positive unless it targets the stub's own attribute, not a rendered child):** A first-pass test for the mobile card list's row-leave animation removed a row from `rows` mid-test and asserted `.app-table-row-leaving` appeared somewhere in `wrapper.html()`. It passed — including after deliberately breaking the feature (`sed`-stripping the `leave-active-class` attribute from the real component) — because `mount()` replaces `<TransitionGroup>` with `<transition-group-stub>`, which removes the leaving element from the DOM immediately with no leave-active-class ever attached to anything, in both the working and broken versions; the assertion's `||` fallback logic made it pass regardless. The fix was to assert on the stub's own `leaveactiveclass` attribute (proving the component is *configured* to play `.app-table-row-leaving` once Vue's real leave logic runs it) rather than trying to catch the class mid-transition — and to verify the fix by literally breaking the feature and confirming the test then fails, the same "prove it has teeth" step this project's own lessons already establish for other classes of bug (see #32's currency-input entry).
**Action:** Before trusting any component test that asserts on a `<Transition>`/`<TransitionGroup>` leave-class/leave-active-class appearing on a *removed* element, check whether `@vue/test-utils` stubbed the transition component (it does, by default, as `<transition-group-stub>`/`<transition-stub>`) — if so, the real leave timing never runs in this environment, and the only honest assertion is on the stub's own configuration attributes, not on catching the class mid-flight. Always deliberately break the feature under test and rerun before trusting a passing assertion involving Vue transition timing, jsdom's lack of a layout engine, or any other environment limitation that can silently turn a real assertion into a tautology.

**Lesson 3 (a shared row-leave timing composable reading a live CSS custom property keeps a JS delay and its CSS animation duration from drifting apart, and automatically inherits the reduced-motion override for free):** `useRowLeaveAnimation`'s `playLeave` needed to know how long to wait before letting the caller (`deleteEvent`/`bulkDeleteEvents` etc.) remove the row and refetch — hardcoding `200` would have silently drifted from `--duration-base` the moment either value changed, and would NOT have picked up the reduced-motion `0s` override at all, defeating the "no animation blocks input" rule under the one condition it matters most. **Action:** When a composable needs a JS-side delay that's supposed to match a CSS animation/transition duration (not just approximate it), read the live CSS custom property via `getComputedStyle` rather than duplicating the value as a literal or importing a shared TS constant — this is the one case where jsdom's inability to evaluate `@media` blocks (Lesson 1 above) doesn't matter, because in a real browser the same variable read automatically inherits whatever override is currently active, reduced-motion included.

**Lesson 4 (a literal "only use the N defined tokens" acceptance criterion can be silently unmet by a plausible-looking magic number, and nothing in lint/type-check/tests/functional review catches it):** The first pass of `useCountUp` (the dashboard count-up animation) hardcoded `600` as VueUse `useTransition`'s duration and passed no `transition` (easing) option at all, defaulting to linear — functionally correct-looking (the security, architecture, and live adversarial e2e reviewers all independently verified the count-up genuinely animates and genuinely suppresses under reduced motion) but a direct violation of PRD-010's literal, checkbox-level acceptance criterion "all motion uses the two duration and two easing tokens from the design foundation" (`--duration-fast`/`--duration-base`, `--ease-out-token`/`--ease-in-out-token`). None of the three parallel reviewers (security, architecture, live e2e) caught it, because each was checking "does this work / is this safe / is this layered correctly" rather than literally re-reading the acceptance-criteria checklist against every numeric literal in the new code. Caught only by the orchestrator re-reading the issue's acceptance criteria line by line against the diff during its own §6 verification pass, after all three review agents had already returned clean.
**Action:** When a PRD/issue states a closed-set constraint as a literal, checkbox-phrased acceptance criterion ("only use the N defined X", "every Y comes from a token"), grep the new code for the actual token names/values after implementation and confirm every relevant literal traces back to one — don't rely on functional/security/architecture review alone to catch this class of gap, since a hardcoded value that happens to produce correct-looking behavior gives every other review angle nothing to flag. This is a distinct failure mode from a functional bug: the code works, and is still non-compliant.

## [2026-09-24] Dashboard visual design — cards-everywhere audit and a new hand-built component (issue #43)

**Category:** frontend | process
**Context:** Applied PRD-010's dashboard-presentation rules to the already-functional dashboard (#38/#42): larger headline type, a secondary percentage figure, a new `StatusDistributionBar` replacing the per-status `el-progress` rows, and dropping `el-card` from sections the PRD doesn't call meaningful. A single-owner, view-scoped presentational change with no contract/backend surface — no parallel team was spawned (feature-team.md's own fitness check: one teammate role, tightly coupled on one file), built directly instead.

**Lesson 1 (an interface's own component styles override an inherited Tailwind utility, even though font properties are normally inherited):** Adding a `text-screen-heading`-equivalent Tailwind class directly to `<el-statistic class="...">` did nothing to the rendered number size. `font-size` *is* inherited by default, but Element Plus's own `statistic.scss` sets `font-size` explicitly on the nested `.el-statistic__content`/`.el-statistic__number` elements — an explicit rule on the element itself always wins over whatever would have been inherited from an ancestor, regardless of specificity. The fix was a scoped `:deep(.el-statistic__content) { font-size: var(--text-screen-heading); ... }` targeting the library's own class, not the wrapper.
**Action:** Before assuming a Tailwind class applied to a wrapping element will restyle an Element Plus component's internals via inheritance, check whether that library component's own `theme-chalk` SCSS sets the target CSS property explicitly on the specific nested part — if it does, inheritance cannot reach it and a `:deep()` override targeting that exact library class is required instead.

**Lesson 2 (a type exported from a `.vue` SFC is not resolvable from another file the way auto-imported composables/components are):** Declaring `export interface IStatusDistributionEntry` inside `StatusDistributionBar.vue` and referencing it from `Dashboard.vue` via `computed<IStatusDistributionEntry[]>(...)` with no import type-checked as `Cannot find name 'IStatusDistributionEntry'` — this project's auto-import registry covers the *component* (the `.vue` file's default export) but not named type exports from it. The established, already-precedented fix (`src/components/data-table/data-table.types.ts`) is a sibling `<name>.types.ts` file with a plain `export interface`/`export type`, manually imported (`import type { ... } from './status-distribution-bar.types'`) wherever needed — consistent with code-conventions' "don't export a type used only in its own file... ≥2 files = move it to the right shared location."
**Action:** Any prop/entry shape a new component needs to share with its parent (not just its own internal `defineProps<...>()`) belongs in a sibling `.types.ts` file from the start, not declared inline in the `.vue` file — check for an existing `*.types.ts` sibling pattern before assuming a type needs to live wherever it's first used.

**Lesson 3 (`fullPage: true` screenshots this app's outer document, which is never taller than the viewport — the actual scroll happens in a nested `el-main`):** A `browser_take_screenshot({ fullPage: true })` at 375×1200 came back exactly 375×1200 with content visibly cut off mid-page, even though there was clearly more below the fold. `AdminLayout`'s `<main class="el-main">` is the app's real scroll container (fixed-height shell, internal `overflow-y: auto`); `document.documentElement`'s own scroll height never exceeds the viewport, so Playwright's "full page" capture — which walks the *document's* scroll extent — has nothing extra to capture. Confirmed via `browser_evaluate` reading `.el-main`'s `scrollHeight`/`clientHeight` (1844 vs 1136), then scrolling that element directly (`main.scrollTop = main.scrollHeight`) before a normal viewport screenshot to see the rest.
**Action:** When a `fullPage` screenshot in this app looks suspiciously exactly viewport-sized with content that should overflow, don't trust it as "that's everything" — `browser_evaluate` the layout shell's own scroll container (`.el-main`) for `scrollHeight` vs `clientHeight`, and if they differ, scroll that element directly and take additional viewport screenshots rather than relying on `fullPage` to reach it. Also: this container's Playwright browser binary was not preinstalled — `browser_navigate` failed with "Browser... is not installed" on first use this session, fixed with `npx @playwright/mcp install-browser chrome-for-testing` before any e2e check could proceed; worth trying that command first if a fresh container's first browser action fails the same way, rather than assuming Playwright MCP itself is broken and skipping to `needs-manual-qa`.
